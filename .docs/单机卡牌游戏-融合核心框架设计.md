## 一、设计目标与边界

**边界**：`Fusion` 程序集 = 融合（组装）机制域——卡套、部位卡、槽型、装卡、召唤费公式、攻血底数、防御性校验。**融合发生在战斗外（整备阶段）**：部位卡装入卡套的槽位，装好的整包（MonsterSleeve）交给战斗核心消费。本程序集不含任何战斗行为，也不含效果执行。

| 维度 | 决策 |
|---|---|
| 纯净性 | 纯 C#，零 UnityEngine——由 `Fusion.asmdef`（`noEngineReferences: true`）编译期强制 |
| 依赖 | `Fusion → Battle`（卡牌配置引用效果描述符）；无人依赖 Fusion（未来战斗核心依赖两者） |
| 无 IO | 不碰文件、不碰路径；一切数据经配置 POCO 构造注入（未来由 Loader 导表产出） |
| 可测试性 | 可脱离 Unity 单独编译运行：dotnet NUnitLite 冒烟 + EditMode 测试双通道 |
| 数据驱动 | 效果=POCO 描述符（来自 Battle）；**新卡=新数据，零代码改动**（补丁方案文档的硬要求） |
| 无随机 | 融合域零随机 |

**程序集与命名**：扁平 namespace `Fusion`（承重墙是 asmdef，namespace 只是门牌）。测试程序集 `Fusion.Tests`（仅 Editor，引用 Fusion + Battle + NUnit）。

## 三、融合规则（策划案 v2.1 → 代码对照）

| 规则 | 实现要点 |
|---|---|
| 召唤费公式制 | `MonsterSleeve.SummonCost` = `max(0, round(Σ部位费 × 乘数, AwayFromZero) + 定值)`；**先乘算取整再加定值** |
| 攻血归属 | 底数 = Σ身材槽部位攻血（**先求和**）× 卡套 `StatMultiplier`；**卡套本体无任何数值**（布局即身份） |
| 卡槽四型 | `SlotType { Body, OnSummon, Continuous, OnLeave }`；部位卡声明槽型，`Install` 校验槽型匹配、槽为空、且符合内容矩阵（§4） |
| 装入 API | `MonsterSleeve.Install(slotIndex, part)`——整备期最小 API；越界 / null / 槽占用 / 槽型不匹配 / 矩阵违例均抛异常 |
| 召唤前置 | `Validate()` 只做**防御性**校验（缺身材槽部位卡抛异常）；合法性由整备阶段保证【约定】 |
| 槽内卡不充能 | 部位卡 `Cost` 写死、召唤时一次付清（充能档位是战斗域概念） |
| 效果槽载荷 | 见 §4——Effects（槽型路由）/ Triggers + Auras（常驻）/ GrantTags |
| 关键词 | `GrantTags`（字符串标签名，如 `"Keyword.Taunt"`）随召唤赋予宿主单位——载体从位标记枚举换为标签（技能系统定义） |
| 消耗标记 | `Consumable`：单位死亡时随包销毁、战后不回收；回收/销毁清单由未来战斗终局产出 |

**随战斗移除的规则域**（重写时按策划案 v2.1 重新立项，不属本文）：回合循环与阶段机、命令 API 与失败原因、事件广播、敌方 AI 与意图、行动点与回复框架、牌区、单位与场面、伤害/治疗/光环结算、胜负与战利品回收、表现挂起。

## 四、部位卡载荷与槽型×内容矩阵

部位卡的行为载荷四字段，类型与语义全部来自《技能系统设计》第五节：

| 字段 | 类型 | 语义 |
|---|---|---|
| `Effects` | `EffectGroupDef[]` | 行为效果组；触发时机由槽型路由：OnSummon=召唤时一次、OnLeave=死亡时一次 |
| `Triggers` | `TriggerDef[]` | 事件触发行为（"受伤反弹""攻击后成长"类）——**仅常驻槽合法** |
| `Auras` | `GameplayEffectDef[]` | 静态光环（挂上时施加的持续效果）——**仅常驻槽合法** |
| `GrantTags` | `string[]` | 随召唤授予宿主单位的标签 |

**槽型×内容合法性矩阵**【约定】（`Install` 防御性校验，数据配置错误在装配期暴露）：

| 槽型 | Attack/MaxHp | Effects | Triggers / Auras | GrantTags |
|---|---|---|---|---|
| Body（身材槽） | ✅ | ❌ | ❌ | ✅ |
| OnSummon / OnLeave（效果槽） | ❌ | ✅ | ❌ | ✅ |
| Continuous（常驻槽） | ❌ | ❌ | ✅ | ✅ |

**导表落点**：配置 POCO 即未来 JSON 的形状（无参构造、公开字段，Newtonsoft 直接反序列化）。`Tests/SampleData.cs` 是活样例：

```json
{ "Id": 113, "Name": "怨念", "SlotType": "OnLeave", "Cost": 1, "Consumable": true,
  "Effects": [ { "Target": "OpposingLeader", "Ops": [ { "Amount": { "Kind": "Const", "Value": 3 } } ] } ] }
```

**补丁纪律提醒**：加卡/改数值=改数据，补丁可行；**新增 EffectOp/Condition/GameplayEffect 字段=表结构变化，必须出整合包**（板块划分文档的纪律）。

## 五、与 Battle 技能系统、未来战斗核心的分工

```
Fusion（本域）           = 卡与卡套的"静态定义 + 装配"（数据容器，零执行）
Battle·技能系统          = 效果如何表达与结算（实体/标签/效果/事件，gameplay-agnostic）
未来战斗核心（入 Battle） = 效果何时被触发（回合/召唤/死亡/意图/UI 事实广播）——技能系统的宿主
```

召唤时的接线形状【约定】（执行归未来战斗核心）：`PartsOf(OnSummon/OnLeave)` 的 Effects → `engine.Execute`；`PartsOf(Continuous)` 的 Triggers → `engine.RegisterTrigger`、Auras → 经 `ApplyEffectOp` 施加；`GrantTags` → 加入单位标签容器。详见《技能系统设计》第九节宿主接入指南。

## 七、扩展指南（按改动类型查表）

| 要做什么 | 改哪里 | 改的是代码还是数据 |
|---|---|---|
| 新部位卡 / 新卡套 | 配置 POCO 实例（未来=JSON 表） | **纯数据** |
| 新效果操作 / 新条件 / 新持续效果策略 | Battle 程序集（见《技能系统设计》第十节） | 代码（=整合包） |
| 接入 JSON 导表 | Loader 读表反序列化成配置 POCO → 局外/整备域组装 `MonsterSleeve` | 代码（Loader 侧） |
| 整备编辑 / 整备 UI | 直接用 `MonsterSleeve.Install / Validate`（战斗核心不参与） | 代码（局外侧） |
| 重写战斗核心 | 进 `Battle` 程序集，按策划案 v2.1 立项，消费本域卡套 + 技能系统引擎 | 代码（新域） |

**已知边界与不做**：部位卡费用写死（无充能）；`Consumable` 只是被数据携带，回收清单产出在战斗终局；本程序集无随机、无事件、无命令——行为面只剩 `MonsterSleeve` 的装槽/公式/校验。
