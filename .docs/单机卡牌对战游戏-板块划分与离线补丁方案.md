# 单机卡牌对战游戏：板块划分与离线补丁方案

> 整理自 2026-10-13 讨论。背景：想做一个本地单机卡牌对战游戏（给几个朋友玩，无服务器），梳理需要的板块，并讨论了"脱离安装包更新"的简化热更方案。

---

## 一、卡牌对战的板块划分（借鉴清单）

| 板块 | 内容 | 备注 |
|---|---|---|
| 1. 卡牌数据层 | Excel/JSON 配置表 → 运行时对象；卡牌 ID/费用/攻血/技能/稀有度；抽卡规则表、卡组表 | 数值不写死在代码里 |
| 2. 卡牌运行时对象 | 配置数据（静态）与战场实例（动态）分离；buff/debuff、持续回合、触发时机（入场/死亡/回合开始） | 效果系统是复杂度核心 |
| 3. 战斗核心 | 回合制状态机：抽牌→出牌→结算→结束；结算顺序、效果链先后 | 用显式状态机或事件队列管理 |
| 4. AI 对手 | 从随机出牌 → 启发式打分 → 简单搜索 | 先做最笨的能跑，再迭代 |
| 5. 牌库与随机性 | 洗牌、抽牌堆/弃牌堆、可播种随机数（方便复现 bug） | pity 机制后期再加 |
| 6. 局外系统 | 卡组编辑器、收集/解锁、PVE 关卡推进、存档 | 存档方案早点定 |
| 7. 表现层 | 出牌动画、伤害飘字、手牌扇形排布 | 表现与逻辑分离，逻辑先在纯数据层跑通 |
| 8. UI 框架 | 窗口管理、界面切换 | 可平移 ET/Ugui 的窗口管理思想 |

**优先级建议**：3（战斗状态机）和 2（效果系统）是难点和决定游戏寿命的部分，先花时间设计；其他是常规工程活。

---

## 二、热更体系一般包含的事

热更的本质：**把"会变的东西"从安装包里剥离出来，运行时下载/替换**。

1. **配置表/文本热更**：数值表、活动文案、公告、开关参数。与资源热更同一条链路。
2. **资源热更**：AssetBundle/Addressables 打包 + CDN + 版本清单增量下载。换活动图、上新卡面不用发包。
3. **代码热更**：
   - Lua 系（xLua/toLua）：成熟但要学第二语言
   - ILRuntime：C# DLL 解释执行（本项目在用，坑多：跨域委托、绑定生成）
   - HybridCLR：近年主流，直接写原生 C#，新项目首选
   - 受限：原生层/SDK、引擎本身；iOS 有政策约束
4. **版本管理与强更**：版本清单 → 决定热更补丁还是跳商店强更。

### 按需分档

| 档位 | 内容 | 适合 |
|---|---|---|
| L0 | 不热更，更新=重新下载 | 纯单机、内容不常改 |
| L1 | 只热更配置表 | 单机但有数值调优需求 |
| L2 | 配置表 + 资源（推荐 YooAsset） | 想换皮、上新卡面 |
| L3 | 加 HybridCLR 代码热更 | 持续运营 |

**单机卡牌的实际建议**：大概率只需要 L1 甚至 L0。更有价值的是**把卡牌效果做成数据驱动**（效果系统 + 表描述效果），上新卡牌/调技能天然就是改表，用架构设计换掉热更需求。

## 三、离线资源包模式（Mods 手动补丁）

**场景**：无服务器，把资源传给朋友，他们自己下载放进目录。

**定性**：算热更（目的上），更准确的名字是"手动补丁/离线资源包"，本质是 **Mod 机制 = 热更的手动挡**。判断标准：玩家是否不用重装/覆盖主程序就拿到新内容。

**决定性前提**：游戏必须支持从外部目录加载资源（Unity 默认只加载打进包里的资源）。

约定目录示例：

```
游戏目录/
  └── Mods/
       ├── cards_新卡牌包.json     （配置表）
       ├── cardart_xxx.png        （图片）
       └── xxx.bundle             （可选，AB资源）
```

游戏启动扫描 `Mods/`，有配置覆盖默认表、有图优先加载。

**实操提醒**："几个朋友玩"的规模下，优先走 **JSON 配置 + 散图**，不要用 AssetBundle（AB 与 Unity 版本绑定，换版本重打主程序后旧 AB 可能失效）。

## 四、Mods 文件夹不会越堆越多：覆盖层与收敛

心智模型：Mods 是"**覆盖层**"，不是"堆积层"。

1. **补丁是全量替换单个文件**：改 3 张卡，发的是改好后的完整 `cards.json`，覆盖旧的——不是增量追加。
2. **攒够了发新版本收敛**：
3. **加载优先级**：`Mods/ 有 → 用 Mods 的；没有 → 用包内的`。任何时候清空 Mods，游戏退化回最近一个正式版。

```
1.0 安装包 ──> Mods 里 v1.1 补丁 ──> v1.2 补丁 ──> 攒多了
                                                        │
2.0 安装包（= 1.0 + 所有补丁 整合重打） <────────────────┘
 Mods 清空，回到干净状态，继续攒 v2.1、v2.2……
```

收敛周期：改烦了的时候 / 换 Unity 版本重打工程时，顺手出整合包。

好处：朋友清空 Mods 就能复现"干净版"，排查问题沟通成本低。

## 五、简单工具流

```
[内容源] → [一键打包] → [分发渠道] → [一键安装]
   你        Editor脚本      网盘/群      朋友的.bat
```

1. **内容源**：工程里约定 `PatchSource/` 目录，所有可热更内容（卡牌 JSON、卡面图、文案）只放这里。
2. **一键打包**：Unity Editor 菜单 `Tools/打补丁包`：复制 `PatchSource/` → `Patch_v1.x/`，生成 `manifest.json`，压缩成 zip。

   ```json
   {
     "version": "1.3",
     "minAppVersion": "1.0",
     "files": ["cards.json", "art/xxx.png"]
   }
   ```

   `minAppVersion` 防止朋友没装新整合包就打新补丁（补丁用了主程序里不存在的字段）。
3. **分发**：网盘/微信群即可。可选偷懒方案：**Git 仓库当"伪服务器"**——Gitee/GitHub 建补丁仓库，朋友 `git pull` 即更新，免费获得版本历史，零服务器成本下最接近自动更新。
4. **一键安装**（可选）：3 行 .bat，双击把 Patch 拷进 `Mods/`：

   ```bat
   @echo off
   xcopy /E /Y "%~dp0Patch" "%~dp0..\Game\Mods\"
   echo 补丁安装完成
   pause
   ```
5. **游戏内加载器**（唯一要写进游戏的代码）：启动读 `Mods/manifest.json` → 校验 `minAppVersion` → 建立"Mods 优先"加载规则。

**最小可用版本**：`PatchSource/` 目录约定 + 手动压缩 zip + Mods 优先加载，三件事就够。manifest 和 .bat 等补丁多到自己记不清时再补——工具流跟着痛点走。

## 六、导表文件放置与补丁数据流（已推演确认）

### 导表产物三分法

| 产物 | 放哪 | 进不进补丁 |
|---|---|---|
| 生成的 C# 类 | 工程代码目录，进 git，随主程序编译 | ❌ 永远不进 |
| 运行时数据 JSON（全量表快照） | `GameData/` 母本，出整合包时复制进安装包 | 整合包时整体更新 |
| 补丁数据 | `PatchSource/` → zip → 朋友的 `Mods/` | ✅ 就是它 |

> 【v1.1 补注】效果卡/部位卡不走 Excel→ConfigGen 腿：结构化效果数据（效果树/条件嵌套/充能档位）由**技能编辑器**（GraphView 可视化编辑，`Assets/CardAuthoring/` 的 SO 为源）直接导出 `GameData/effect_cards.json`、`part_cards.json`。纪律不变：改数值=补丁可行；新增效果操作类型=代码变化=必须出整合包。Excel 仍管纯数值表（卡套/关卡等），表格与编辑器以卡牌 id 关联。**文件即工具所有权：一个 JSON 文件只有一个产出工具。**

### 目录结构与三目录身份

```
TruckCardGame/                 游戏运行目录 Game/
├── Excel/                     ← 源头（原稿），只由人编辑      ├── TruckCardGame.exe
├── Tools/                     （导表脚本）                    ├── Config/   ← 基线（安装时从 GameData 复制）
├── Unity/Assets/Scripts/                                                      │ 加载优先级 Mods > Config
│      ConfigGen/              ← 生成 C# 类，进 git             └── Mods/    ← 覆盖层（补丁落地）
├── GameData/                  ← 最新母本，只由导表工具刷新
└── PatchSource/               ← 快递箱，只由打包按钮生成，可扔
```

**PatchSource 里的文件永远不要手工编辑**——它是纯产物，发现内容不对回 Excel 改再重打。

### 补丁推演（v1.0 → 1.3）核心结论

- v1.0 发布 = `GameData/` 复制成安装包的 `Config/`，Mods 为空，三层同一份内容。
- 补丁**只含相对上次变了的文件**：改 levels.json → 补丁里只有 levels.json（+ manifest）；下次只改 cards.json → 补丁里没有 levels.json。
- 每个补丁文件是**全量自足**的（含此前所有改动，因为母本 GameData 从不回退），不依赖之前装过什么补丁；新补丁覆盖 Mods 里的同名旧文件。
- manifest 的 `files` 列表只描述"这个补丁带了什么"，**不是卸载清单**——旧补丁装进 Mods 的文件继续生效。
- 收拢成一句话：**GameData 是唯一的"最新全集"；每个补丁只是"相对上个补丁以来变了的那几个文件的最新版"；Mods 是历次补丁落地的并集。**

### 四条纪律

1. 生成的 C# 类不手改（要加辅助方法用 partial class / 扩展方法另放）。
2. PatchSource 不手改，删了重打即可。
3. 生成代码不进补丁：**改数值=补丁可行；改表结构（加字段）= 生成类变化 = 必须出整合包**。
4. 卡牌效果做成数据驱动（通用效果解释器 + 表描述），新卡只是新数据，永远走补丁。

### 打包按钮怎么知道这次改了什么

二选一：① 对比快照——出整合包时存一份上版基线，打包时文件级 diff，精确但要存快照；② 手动勾选——打包窗口列 GameData 文件自己勾，实现最简，漏勾下次补丁补上即可。几个朋友玩推荐 ②。
