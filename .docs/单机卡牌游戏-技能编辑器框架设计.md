# 单机卡牌游戏：技能编辑器框架设计

> 状态：v1（2026-10-17，随第一版实现落地，代码即本文的权威来源）。
> 分工：与《单机卡牌游戏-技能编辑器策划案》互为配套——**策划案定"UI 长什么样、要哪些功能"，本文定"代码怎么组织、数据怎么流、怎么拓展"**。规则与数据所有权以《战斗核心机制策划案》v2.1 与《目录结构与资源加载》为准。
> 代码位置：`Unity/Assets/Scripts/CardAuthoring/`（+ Editor 子目录）；编辑源资产 `Unity/Assets/CardAuthoring/`；导出产物 `GameData/effect_cards.json`、`part_cards.json`。

## 一、定位与边界

| 维度 | 决策 |
|---|---|
| 是什么 | 效果卡/部位卡的可视化 authoring 工具——仿 XHFrameworkSkillDemo 的 GraphView 编辑体验，产出本项目战斗核心的数据形状 |
| 不是什么 | 不是运行时系统：战斗核心（`Battle`）已有数据驱动效果解释器，本工具只做"编辑→编译→导出"，零运行时代码 |
| 编辑对象 | 效果卡（充能档位 + 效果树）、部位卡（槽型/身材/费用/关键词/消耗 + 效果树）；**不编辑**卡套（表格）、敌人、卡面/描述/正式名称（表格，按 id 关联） |
| 数据归宿 | SO 编辑源（`Assets/CardAuthoring/`，git 跟踪，不进包）→ 一键导出 JSON 母本（`GameData/`）——运行时管线与 Mods 补丁纪律不变 |
| 关联键 | 卡牌 id 一贯到底：Excel 行 ⇄ JSON ⇄ 玩家存档 ⇄ BattleResult；**Excel 不需要 SO 路径列**（id 是身份，路径不是） |

**从参考项目抄了什么/不抄什么**：抄三栏窗口、GraphView+UIToolkit 技术栈、节点+GUID 连线数据模式、右键建节点、Ctrl+S 脏标记；不抄 GAS 全家桶（标签/时间线/投射物/表现节点）、运行时图解释器、约 90% 代码量。

## 二、程序集与文件地图

三个程序集，依赖单向（Editor → CardAuthoring → Battle），**Battle 零改动**（本工具接入时仅补了 `[Serializable]` 标注，无行为变化）：

```
Unity/Assets/Scripts/CardAuthoring/            ← CardAuthoring.asmdef（引用 Battle，可用 UnityEngine）
├── GraphModel.cs            图模型：EffectDefNodeData / OpNodeData / ConnectionData
│                            + PortNames 端口名约定（操作/继续/是/否）
├── GraphCompiler.cs         图 → EffectDef[] 编译器（纯 C#，headless 可测）
├── CardJsonWriter.cs        JSON writer（反射字段、camelCase、判别键）
├── CardJsonReader.cs        JSON reader（递归下降解析 + 反射装配 + 类型注册表）
├── EffectCardAsset.cs       效果卡 SO（TierData：档位=一张图）
├── PartCardAsset.cs         部位卡 SO（整卡一张图）
├── AssemblyInfo.cs          InternalsVisibleTo("CardAuthoring.Editor")
└── Tests/                   ← CardAuthoring.Tests.asmdef（EditMode；NUnit）
    └── GraphCompilerTests.cs    11 用例：链/嵌套条件/孤立/环/空图/JSON 往返×3/判别键

Unity/Assets/Scripts/CardAuthoring/Editor/     ← CardAuthoring.Editor.asmdef（仅 Editor）
├── CardEditorWindow.cs      主窗口（三栏 + 工具栏 + Ctrl+S + 自动保存）
├── EffectGraphView.cs       画布（连线规则/成环拦截/图↔数据双向同步）
├── Nodes/EffectDefNode.cs   效果组根节点（目标模式显示 + "操作"输出端口）
├── Nodes/OpNode.cs          通用操作节点（输入 + "继续" + 注册表分支端口 + 摘要）
├── Nodes/OpNodeRegistry.cs  ★ 拓展点：OpNodeDescriptor 注册表
├── Inspector/CardInspectorView.cs   卡级表单（效果卡档位管理 / 部位卡属性）
├── Inspector/NodeInspectorView.cs   节点参数（反射表单 + 条件类型编辑）
└── Export/CardPoolExporter.cs       导出器（Editor 侧唯一 GameData 路径持有者）
```

**分层职责**：数据层（GraphModel/两 SO）→ 编译层（GraphCompiler）→ 序列化层（JsonWriter/Reader）全部零 UnityEditor 依赖（SO 仅用 UnityEngine），因此整套管线可在 headless 环境（dotnet + NUnitLite）测试；窗口/画布/表单/导出这类必须依赖编辑器的代码全部隔离在 Editor 程序集。

## 三、数据模型

### 3.1 SO 资产（编辑源）

```
EffectCardAsset { id, cardName(工作名), tiers: [ TierData ] }
TierData { cost, label, effectDefs[], opNodes[], connections[] }   ← 一个档位 = 一张独立的图

PartCardAsset { id, cardName, slotType, cost, attack, maxHp,
                grantKeywords, consumable, effectDefs[], opNodes[], connections[] }
```

- 工作名仅编辑期标识；正式名称/描述/卡面归表格（数据所有权见《目录结构》文档）
- **图 = 三张平铺列表**：效果组根、操作节点（带 x/y 位置）、连线（`outputNodeGuid + outputPort → inputNodeGuid`，输入端口唯一无需名）
- 权威源是图：保存/导出时从画布全量重建三张列表，增删节点自动正确；效果组顺序按画布 x 坐标升序（**图左 = 先执行**）

### 3.2 op 子树的持久化：opJson 字符串（关键决策）

`OpNodeData` 不用 `[SerializeReference]` 直接持有 Battle 的 EffectOp，而是存**自家 writer 序列化的 JSON 字符串**（`GetOp()` 惰性解码缓存、`SetOp()` 同步回写）：

| 收益 | 说明 |
|---|---|
| 纯数据层零 UnityEngine | GraphModel/Compiler/JsonWriter/Reader 可 headless 编译测试（SerializeReference 是引擎属性，会把依赖传染进纯层） |
| op 类改名零风险 | SerializeReference 按类型全名绑定资产，改名即丢数据；字符串存储不怕迁移 |
| reader 即未来 Loader 雏形 | writer/reader 由 round-trip 测试强制对称，schema 双向锁定 |

### 3.3 图的合法形态（树，不是自由图）

- **效果组节点**（根）：目标模式（TargetMode 八种）+ 一个"操作"输出端口，无输入
- **操作节点**：一个输入端口 + "继续"顺序输出端口；条件分支操作额外有"是/否"两个分支端口（分支端口是注册表能力，非硬编码）
- 连线约束：输入单进、每个输出端口单出、禁止自环与成环（连线瞬间 DFS 拦截）、效果组只能作根
- 语义：效果 = 顺序链（沿"继续"边）；`ConditionalOp.Then/Else` = "是/否"两条子链——**嵌套条件 = 分支里再接条件节点**
- 编译兜底（数据被手改坏时）：环/菱形引用截断+告警、链长>256 截断、嵌套>32 层截断、空节点跳过、孤立节点告警且导出跳过

### 3.4 编译产物

`GraphCompiler.Compile(effectDefs, opNodes, connections) → Result { Effects: List<EffectDef>, Warnings }`——产出即 Battle 的运行时数据结构，零中间形态。

## 四、JSON 管线

**格式**（判别键 + camelCase，多态不再依赖任何引擎序列化）：

```json
{ "cards": [ { "id": 301, "name": "火球术", "tiers": [
    { "cost": 4, "label": "完全体",
      "effects": [ { "target": "Chosen", "ops": [
        { "op": "Conditional",
          "condition": { "condition": "TargetHpBelowPercent", "percent": 0.5 },
          "then": [ { "op": "Damage", "amount": 6 } ],
          "else": [ { "op": "Damage", "amount": 3 } ] } ] } ] } ] } ] }
```

- 判别键规则：类名去 `Op`/`Condition` 后缀（`DamageOp→"Damage"`、`TargetHpBelowPercentCondition→"TargetHpBelowPercent"`），writer/reader 共用 `EffectJsonNames` 防漂移
- 类型注册表：reader 扫描 Battle 程序集的 EffectOp/ConditionDef 子类——**新增类型自动可解析，无需注册**
- 导出语义：单文件按类聚合（`effect_cards.json`/`part_cards.json`，文件即工具所有权/补丁粒度）、按 id 升序稳定排序（diff 清晰）、重复 id 报错中止、孤立节点告警跳过
- **`CardJsonReader` 就是未来 Loader/ConfigDatabase 装配 GameData JSON 的实现基础**，schema 已被测试锁定

## 五、编辑器实现要点

- **窗口**（`Tools/技能编辑器`）：Toolbar + 三栏（左 230px 卡池列表、中画布、右 330px 卡级表单+节点参数）；保存时机 = 按钮/Ctrl+S、切换资产或档位前、关窗（OnDisable）；脏标记体现在标题 `*`
- **画布**（`EffectGraphView : GraphView`）：ContentDragger/SelectionDragger/RectangleSelector/ContentZoomer + GridBackground；右键分层菜单（效果组 + 注册表全部操作）；非法连线通过 `graphViewChanged` 返回值在创建前过滤
- **节点表单**（`NodeInspectorView`）：按 op 的公共字段**反射生成控件**（int/float/double/bool/string/enum 开箱即编辑）——新操作的参数编辑零代码；条件分支节点额外提供条件类型下拉（注册表驱动）+ 条件参数表单；Then/Else 不在表单编辑（图连线即内容）
- **导出**（`Tools/技能编辑器/导出卡池 JSON`）：先让打开中的窗口保存（保证图结构落盘）→ 逐资产编译 → 校验 → 写 `GameData/`；`CardPoolExporter` 是 Editor 侧唯一 GameData 路径持有者（运行时四持有者不变，编辑期第五个）

## 六、拓展指南（按改动类型查表）

| 要做什么 | 改哪里 | 性质 |
|---|---|---|
| 新效果卡/部位卡 | 编辑器里点按钮 | 纯数据 |
| 新效果操作（如召唤衍生物） | ① Battle 写 op 类（+[Serializable]）② `EffectInterpreter.ApplyOp` 加 case ③ `OpNodeRegistry.Register` 一行（标题/菜单路径/摘要/分支端口） | 代码=整合包；序列化/导出/参数表单全自动 |
| 新条件 | ① Battle 写 ConditionDef 子类 ② `EvalCondition` 加 case | 代码=整合包；注册表自动发现，节点下拉自动出现 |
| 动效类节点（未来） | `OpNodeRegistry` 加类目 + Battle 侧对应数据类 | 预留位：图模型/编译器/序列化不动 |
| 调整窗口布局/表单 | `CardEditorWindow` / 两个 InspectorView | 纯编辑器代码 |
| 接 Loader | 复用 `CardJsonReader.ParseEffectCards/ParsePartCards` 装配 BattleSetup | Loader 侧代码 |

## 八、已知边界与风险

- GraphView 在 Unity 6 仍是 experimental 命名空间（参考项目 2022.3 同款用法兼容）；若日后被移除，迁移成本集中在 `EffectGraphView` 一个文件
- Inspector 直接写对象 + 手动脏标记（与参考项目一致），**不在 Undo/Redo 体系内**——误删节点用"不保存关窗"兜底；接 Undo 是后续可选项
- 删卡需两侧同步（编辑器删 SO、表格删行），未来 Loader 按 id join 报缺兜底
- 重复 id 检测只在导出时触发（编辑期不实时）——卡池变大后可在列表刷新时前置
